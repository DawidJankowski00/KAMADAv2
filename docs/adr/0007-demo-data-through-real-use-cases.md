# 0007. Demo data seeded through the real use cases

- **Status:** Accepted
- **Date:** 2026-09-28

## Context

A reviewer should start the stack and immediately find something to click: accounts, a catalog, clients,
orders in every status, a run planned for today and one completed yesterday. The data spans all modules
(an order references a client and products, a payment an order, a run orders and a courier), yet modules must
not write into each other's schemas and ids are generated by the domain (`Guid.CreateVersion7()`).
Inserting rows with SQL would bypass the business rules the project is about (stock reservation, order totals,
status transitions, route planning) and would easily produce states the application itself can never reach.

## Decision

- Every module registers its own `IDataSeeder`; `DatabaseInitializer` runs them in `SeedOrder` in **one DI
  scope** when `Database:SeedDemoData` is on (Development and the Docker setup):
  Workforce → Catalog → Customers → Ordering → Payments → Ordering (packing) → Delivery.
- Seeders **pass generated ids on through `DemoSeedData`** (a scoped hand-over object): couriers, products,
  shipping addresses and placed orders. Downstream seeders use them only through the other modules' contracts,
  exactly like production code.
- Business data is created **through the real use cases**: `PlaceOrderHandler` (stock reservation, price
  snapshot, total), `PaymentService` (payment + order marked paid), `OrderCommands` (cancel with stock return,
  ready for delivery), `DeliveryRunCommands`, `RoutePlanningHandler` (real optimization with the configured
  matrix provider) and `CourierRunCommands` (start, deliver, fail).
- **History is replayed with a `SeedClock`**: handlers are created with `ActivatorUtilities.CreateInstance`
  and a settable clock, so yesterday's run really starts at 08:30 and stops are delivered along the estimated
  arrival times. `created_at` (stamped on save) is moved back afterwards with `ExecuteUpdate` in the owning
  module – the one place where a seeder writes a column directly.
- Addresses of the 25 clients are **real buildings in the Tricity and Szczecin with stored coordinates**
  (geocoded once with Nominatim when the seed was written), so startup never calls a geocoding service. Random parts (names, e-mails,
  phone numbers, order contents) use Bogus / `Random` with fixed seeds: every fresh database looks the same,
  relative to the current date.
- Seeding runs **only on an empty database**: each seeder skips when its tables already contain data, and a
  seeder whose input is missing skips too. Resetting the demo means recreating the database
  (`docker compose down -v`).

## Consequences

- The demo cannot contain impossible states; if a business rule changes, the seed either follows it or fails
  loudly at startup (an integration test seeds a fresh database and checks the scenario).
- Seeding depends on the matrix provider like real planning does; when it is unreachable the Haversine
  fallback is used and the plan is flagged as approximate.
- `DemoSeedData` names concepts of several modules in shared infrastructure – acceptable because it carries only
  ids and timestamps, never module types.
